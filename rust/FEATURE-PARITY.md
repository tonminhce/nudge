# Feature parity with the upstream CRM

What Nudge has, what it does not, and what it takes to close the gap. Status is measured, not
estimated: every "done" row has a test or a verification script behind it.

Legend: **done** = implemented and verified · **part** = partially implemented · **todo** = not
started. The wave numbers are the ones in [MAP.md](MAP.md).

## Summary

| Area | Upstream size | Nudge today |
|---|---|---|

### Measured checkpoints (2026-11-28)
- Wave 4 live record parity: `tools/record-parity.py` — 13 fixtures, **9 gaps / 10 diffs** measured against the real `twentycrm/twenty:v2.61.0` container (candidate :3000 at `74d140c`, harness after the coverage fix). The earlier "0 gaps / 18 diffs" was a verifier blind spot, not a better result: a scenario that aborted early on Rust left keys the reference had, those missing keys were compared against `None` and counted as DIFF rows, and keys Rust answered but the reference never produced were dropped entirely because the loop iterated only the reference keys. `run()` now walks the union of capture keys, reports a Rust-only capture as a DIFF naming itself, reports a key the Rust scenario never answered as a GAP, and turns a raised exception into one ERROR row carrying the exception instead of one silent `None` diff per key. The same run also classifies the 6 diffs whose Rust body carries `Cannot ...`/`... does not exist`/`GRAPHQL_VALIDATION_FAILED` with an `[absent: CODE]` prefix so an unimplemented shape is never mistaken for a behavioral divergence. Anchors are now deterministic: `resolve_person_id`/`resolve_company_name` select by the seeded names (`Ivan`/`Alice`/`Bob`, then `Acme Corp`/`Initech`) before falling back to first-edge, because a first-edge anchor hides an ordering divergence whenever the two servers disagree on row order — the exact defect this plane is measuring. The diffs group into four root causes, not eighteen: composite fields on the connection path (`Column "nameFirstName" does not exist on "person"` for `people { edges { node { name { firstName } } } }`, also through `orderBy`, and the same column error behind the `or` / `position: { is: "NULL" }` filter rows and the `AscNullsFirst` row), relation writes in create data (both planes answer `Column "company" does not exist on "person"` for `company: { connect: { id } }`, so what diverges is the missing pre-SQL shape validation recorded in the relation-write probe bullet below, not the connect shape itself), bulk create producing invalid SQL (`createCompanies` → `syntax error at or near "0"`, `INTERNAL_SERVER_ERROR`, which cascades into every `merge-many` row), and the REST relation key, where the earlier wording in this file was inverted: measured with `PARITY_DIFF_DEPTH=8`, `body.data.people[0]` carries `companyId: null` on the reference with **no** `company` key at all, while our body carries `company: null` and no `companyId` — the same inversion on `/rest/people/<id>` at `body.data.person`. So 2.61.0's default REST field set exposes a many-to-one relation as `<fieldName>Id` and never as a null bare relation. Plus `Column "edges" does not exist` for a reverse to-many projection (`companies → people`). Matching today: `error-bad-filter`, `bad-cursor` (`BAD_USER_INPUT`/`INVALID_CURSOR`, "Invalid cursor: garbage"), the composite-`ilike` rejection (the reference names the available sub fields), and the REST unknown-object 400 (`BadRequestException`, `object 'nope' not found. eg: companies`). Probing also settled which record fields the 2.61.0 core API does **not** expose: `aggregatePeople`, `aggregateCompanies`, `deleteManyPeople` and `upsertPerson` all come back `GRAPHQL_VALIDATION_FAILED` / `Cannot query field ... on type "Query"/"Mutation"`, so they are not port targets on this plane. The 9 gaps are not nine missing endpoints: 8 of them are the `merge-many` captures (`dryRun`, `merge`, `singleId`, `unknownId`, `badIndex`, `childBefore`, `childAfter`, `secondaryAfter`) that the scenario never reaches because the bulk create fails first and the scenario returns its `abort` capture instead — a Rust-only key the reference run does not have — and the 9th is `orderBy-pagination/page2`, which the aborted `page1` ordering short-circuits. Fixing the bulk-create SQL plus the composite sub-field column resolution therefore moves 9 rows at once, which is why the harness now reports them as unreachable rather than as nine independent divergences. Re-measured after `d8fc2b5` with the candidate rebuilt from `05a5eb9` and restarted on :3000: the totals are still 9 gaps / 10 diffs, but the blocker behind all eight `merge-many` gaps moved — `createCompanies` no longer returns `syntax error at or near "0"` / `INTERNAL_SERVER_ERROR`, it now returns `BAD_USER_INPUT` with `Column "domainNamePrimaryLinkUrl" does not exist on "company"`, and `information_schema.columns` shows `domainNamePrimaryLinkLabel`, `domainNamePrimaryLinkUrl`, `domainNameSecondaryLinks` as real flat columns in **every** `workspace_*.company` table, the same shape the `person` tables carry. - Relation-write probe, measured 2026-11-28 with the `988fcd0`-era candidate on :3000 against the v2.61.0 container on :3001, one shared workspace, `createPerson` only. The wording this file used to carry was wrong (corrected in the bullet above): 2.61.0 does **not** accept `company: { connect: { id } }` — it answers the same `Column "company" does not exist on "person"` we do, because `twenty-2610/packages/twenty-server/src/engine/api/common/common-args-processors/data-arg-processor/data-arg-processor.service.ts:296-301` rewrites only `connect.where` and returns every other relation value untouched. What upstream does before that, at `data-arg-processor.service.ts:267-321`, is validate the shape: ONE_TO_MANY → `One-to-many relation <key> field does not support write operations.`, `key === joinColumnName` → `validateUUIDFieldOrThrow`, a non-nested value → `Relation "<key>" requires create, connect, or disconnect operation`. The live consequences of that difference: scalar `company: "<uuid>"` is `BAD_USER_INPUT | Relation "company" requires create, connect, or disconnect operation` on the reference and `Column "company" does not exist on "person"` on Nudge; `company: { connect: { where: { id } } }` and `company: { create: { … } }` both pass validation on the reference — the nested payload is itself validated, which is how a wrong links subfield produced `Invalid subfield primaryLink for links field "domainName"` and proved the accepted subfield names are the flat `primaryLinkUrl` / `primaryLinkLabel` / `secondaryLinks` ones — while both shapes only ever reach `Column "company" does not exist on "person"` on Nudge, so nested relation writes are unimplemented on our side; `companyId: "not-a-uuid"` is `BAD_USER_INPUT | Invalid UUID value 'not-a-uuid' for field "companyId"` on the reference and `INTERNAL_SERVER_ERROR | A query parameter could not be bound` on Nudge; and a real FK violation is `BAD_USER_INPUT | insert or update on table "person" violates foreign key constraint "FK_ee066ddacfce46c9a7cb90edd1a"` on the reference against `INTERNAL_SERVER_ERROR` with the identical text on Nudge, the same constraint name on both. Finally, the `merge-many` fixture's `childBefore` capture sends `company: { connect: { id } }`, so that capture fails identically on both planes and can never produce a child row until the fixture writes the relation through `companyId` or `connect: { where: { id } }` — it is a harness defect, not a ninth server gap.
